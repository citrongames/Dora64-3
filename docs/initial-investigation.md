## Загрузка и оверлеи

Входной код [0x80025C00,0x80025C3C) очищает
[0x8007EA80,0x800FECB0), устанавливает SP=0x80085A00 и выполняет
косвенный переход на 0x80027414. Эти эффекты проверены исполнением
сгенерированного C на Linux и Windows с контролем всей 4-МиБ области памяти.

Резидентное отображение начинается ROM 0x1000 → RAM 0x80025C00.
Граница ROM 0x59E80 соответствует началу BSS 0x8007EA80 и началу первого
дополнительного блока. Не считать весь резидентный диапазон CPU-кодом:
в нём находятся данные и RSP-программы.

Функции 0x800430B8…0x8004335C образуют 14 прямых загрузчиков.
Их ROM start/end и RAM destination восстанавливаются из `lui/addiu`;
`jal 0x8002730C` получает длину end-start в delay slot.
Полная машинно проверенная таблица: `research/layout-report-v2.json` → `fixed_loads`.
Например:

| ROM [start,end) | RAM start | Вызывающий загрузчик |
|---|---|---|
| 0x59E80…0x5E400 | 0x801B3770 | 0x800430B8 |
| 0x5E400…0x635C0 | 0x801B3770 | 0x800430EC |
| 0x635C0…0x70A50 | 0x801B8ED0 | 0x80043154 |
| 0x70A50…0xCEC60 | 0x801B8ED0 | 0x80043120 |

Несколько блоков занимают одни адреса: одной таблицы VRAM→function для всей
игры недостаточно. При загрузке надо менять активную регистрацию ROM/секции.
Границы функций внутри блоков, все дополнительные загрузки, BSS блоков и
наличие релокаций ещё не установлены. 14 — число найденных фиксированных
загрузчиков, **не** доказанное общее число оверлеев.

0x8002730C — синхронная обёртка чтения с cache operations, чанками до 256 байт
и ожиданием сообщения; 0x8004ED00 соответствует интерфейсу osEPiStartDma
по аргументам/OSIoMesg. Имена SDK пока кандидаты, кроме проверенной семантики.

## Сжатие

Сканер не нашёл MIO0/Yay0/Yaz0/RNC/gzip/ZIP magic. Это не означает отсутствие сжатия.
По коду 0x800340E8 восстановлен вариант LZSS: нулевой словарь 1024 байта,
начальная позиция 0x3BE, флаги младшими битами вперёд; 1 = literal,
0 = ссылка. Индекс `low | ((high & 0xC0) << 2)`, длина `(high & 0x3F)+3`.

Записи имеют 16-байтовый заголовок: flag, reserved, packed_size, decoded_size
как big-endian u32. Наблюдаемые flag 0/1; следующий заголовок выровнен на 16 байт.
С ROM 0x1C5DE0 разобраны 3129 подряд идущих записей; заявленные размеры совпали.
На 0x56FC30 последовательный обход остановлен: следующая структура не установлена.
Это не полный каталог всех игровых ресурсов и ещё не каталог текста/текстур.

Проверка против исходной рекомпилированной функции: 11 выбранных сжатых записей,
включая первую, последнюю, крупнейшую и распределённые по диапазону, совпали
побайтно. Сохраняются только хэши/размеры, не распакованные данные.

Выявлено важное отличие от абстрактного memcpy: потоковый читатель просит
0x3FF байт, но потребляет 0x400 и продвигает ROM-позицию на 0x400.
Последний 255-байтовый PI DMA аппаратно округляется; подтверждение модели есть
в `pi_controller.c` Mupen64Plus (нечётные длины >=0x7F).
Точное копирование 1023 дало 34703 байта вместо 34728 на первом образце.
Учёт этого конкретного округления дал полное совпадение выборки.
В Dora64 runtime `do_dma`/`do_rom_read` такого округления нет: это отдельный
пункт будущей интеграции третьей игры, не повод менять рабочий Dora64.

## Микрокоды

В ROM присутствуют строки F3DEX/S2DEX/L3DEX fifo 2.08, F3DEX/F3DLX/
F3DLX.Rej/F3DLP.Rej/L3DEX 1.23, S2DEX 1.07 и RSP SW Version 2.0H.
`identify_microcode.py` сравнивает XXH3 по порядку байтов RDRAM с базой
зафиксированного RT64; результат в `research/microcode-report-v2.json`.
Совпадение диапазона — идентификация присутствующего блока, не доказательство
того, что игра реально отправляет его в OSTask.

В RT64 есть F3DEX/F3DEX2/S2DEX/S2DEX2/L3DEX2 handlers; L3DEX 1.23 помечен
`GBIUCode::Unknown`. Используется ли этот блок в игре, пока неизвестно.
Аудио/RSP entry, диапазон aspMain, непрямые переходы и возможные иные задачи
не определены. `aspMain` первой игры и его offset 0xA80B0 не переносились.
