# Widescreen: анализ и архитектура, 2026-10-10

Статический анализ перед реализацией. Основа: main `7df7634`, принятая пользователем Windows test095. На начало задачи рабочее дерево чистое. Donor Dora64: `680d81f`, только чтение. ROM SHA256 `410f99bdd58795639da272c9be9d1ab8c35b61f24f7c1fb92f7e83e1069a2602`. Исходные инструкции читались из актуальной генерации `startup-modern-camera-v2` и сопоставлялись с оригинальной структурой ROM. В `research/widescreen-analysis.json` сохранены ROM fingerprints выбранных тел, прямые вызовы и инвентаризация больших BMP.

Это проект решения, а не готовая функция. Игра, CPU checks, тесты, renderer и GPU не запускались. Декодирование ресурсов ниже — чтение сжатых данных ROM, без исполнения игровых функций. Нет нового EXE, коммита или push. Реализация — после команды пользователя; сборка в конце разрешённой реализации по действующей договорённости, commit/push после его проверки.

## Настройки Dora64

`src/system_overlay.cpp:821–832,893–902`: Graphics, сразу после Game render resolution:

| Поле | Варианты |
| --- | --- |
| Game aspect ratio | Original (4:3); Fit to window / fullscreen |
| Gameplay HUD layout | Original (4:3); Fit to window / fullscreen |

Потом идут Anti-aliasing и Texture filtering. В Dora64-3 сглаживания сейчас нет: новые два поля вставить между resolution и filtering, не добавлять побочную функцию MSAA. В donor JSON `graphics.aspect_ratio` и `graphics.hud_layout`; `rt64_render_context.cpp` направляет их в независимые RT64 `aspectRatio` и `extAspectRatio`. Original profile выбирает обе Original; Modern — обе Expand/Full. Старые конфиги третьей игры без этих полей должны продолжить 4:3 до явного выбора или применения Modern profile. Обновить устаревшую подсказку третьей игры, что оба профиля сохраняют 4:3.

Режим Fit вычисляется из фактического drawable окна, а не фиксируется на 16:9. Обработать resize, fullscreen, HiDPI, минимизацию и узкие окна; при пропорциях уже 4:3 разумно сохранять полный исходный кадр с полями, не обрезать вертикаль. HUD Fit в режиме изображения Original фактически остаётся внутри его 4:3 области; настройку можно сохранить для последующего включения widescreen.

## Что уже умеет рендер и почему одного переключателя мало

`src/live_graphics.cpp` жёстко задаёт RT64 Original; `apply_graphics()` сейчас учитывает resolution/filtering/FPS, но не aspect/HUD. RT64 уже умеет расширять перспективу: `rt64_projection_processor.cpp` корректирует горизонтальный столбец матрицы, сохраняя вертикальный FOV. Это подходящая основа; нельзя одновременно менять оригинальный aspect аргумент SDK и ещё раз применять RT64 correction.

Закреплённый fork RT64 содержит правила первой Dora64 в `rt64_framebuffer_renderer.cpp`: texture hashes hearts/camera HUD, размеры 16×16, donor sky mosaic, EPOCH fades, финальные переходы. Это не правила Dora64-3. Нужен локальный адаптер копии исходника с проверкой fingerprint, по существующему образцу `tools/prepare_rt64_framerate.py`; не править donor, pinned dependency checkout или generated C вручную. Отделить donor эвристики от стандартной коррекции RT64. Размечать третью игру по подтверждённому вызывающему коду/слою, а не по цвету или похожему размеру прямоугольника.

В RT64 доступны extended commands для projection groups/aspect, signed texture rectangles, viewport/scissor и origin left/center/right. Они позволяют выразить смысл слоя без глобальной замены всех экранных координат. Оригинальные 12-bit команды и CPU clipping bitmap builder не позволяют просто дать обычному спрайту отрицательный X.

Данные извлечены и визуально просмотрены локально. Картинки не включать в Git/пакет: ресурс получать из пользовательского ROM. BC7 не обязательно живёт в guest cache карты/другого экрана. Для общей подложки нужен собственный immutable ресурс на сессию: однократное декодирование при загрузке ROM, затем texels/TLUT с корректным lifetime до graphics reset barrier. Не брать старый guest handle после смены overlay и не декодировать/загружать с диска каждый кадр.

File screen: `.scene34` `801BD7F8` читает пары resource/slot с `801C3C84`; BC7 записывается в slot41, handle `801C67A2`. `801BDA88` рисует этот фон первым bitmap в(0,0), затем надписи/кнопки; callback `801BFC44` рисует ещё три двери и выбор. Расширение касается фонового вызова, двери/надписи сохраняют пропорции и композицию.

Можно позднее расширить видимую часть настоящей карты, но тогда нужно согласованно переделать границы выборки, отображение узлов, clipping и край карты; для первой реализации это лишнее изменение поведения навигации. ## 3D, HUD и специальные экраны

По прямым JAL в оригинальном ROM найдены26 вызовов общего perspective builder `8002F20C`. Он вызывает `800578B0` (cot(FOV/2), деление по aspect, near/far, conversion). Загрузка выбранной projection — `8002F4E0`; view/look-at — `8002F2C8`. Обычный world render `.scene1/801BB334` передаёт исходный aspect4/3, near20 и far20000; текущая дальность уже отдельно адаптирует far. Widescreen сохраняет вертикальный FOV, zoom, near/far и действующий draw-distance control.

Горизонтальное расширение не связано с разрешением Modern camera по кнопкеZ. Обычная фиксированная камера может показывать широкий кадр, оставаясь фиксированной. Не изменять camera owner, управление, FPS equations или скриптовый маршрут ради widescreen. Для катсцен3D расширять вид, а авторские маски/2Dиллюстрации сохранять по роли. Отдельно учитывать полноэкранные flash/fade и панели диалогов; shader/overlay с aspect AUTO не является гарантией правильной классификации.

Миниигры требуют разметки всех9 draw callbacks. Пример `.minigame_1/801CB160`: один perspective setup, затем четыре view records и четыре static DL viewport/scissor, после чего возврат к общему HUD. Это настоящий многовидовой путь. Для него нужна коррекция каждого прямоугольника и его aspect, сохранение разделителей/границ и HUD участников; полный общийviewport на каждый draw приведёт к наложению видов. Не оставлять весь режим случайно зависящим от RT64 auto detection coversWholeWidth.

Общий bitmap builder `8002A844` имеет197 прямых вызовов и CPU clipping/chunking, TLUT, CI4/CI8/16-bit paths. Он обслуживает и HUD, и диалоги, и карту, и меню. Нельзя переносить всё, что попало в угол, к краю. Ввести явные группы:

- World3D / SplitWorld3D: расширенная перспектива с исходным vertical FOV.
- CenteredComposition: title letters, двери, иконки меню, карты/иллюстрации и связанный текст.
- HudLeft / HudRight / HudCenter: привязка целой смысловой группы, включая рамку, цифры и meter.
- TiledBackground: свой период/фаза/палитра.
- FullscreenEffect: широкий fade/flash/clear, отдельный от частичного UI rectangle.

`801BED6C` вызывает HUD meter; charge rectangle уже имеет Native adapter в `native_ui.cpp`. Текст/иконки/рамки должны получать одинаковое смещение. UI panels `scene_common/801B5E44`, диалоги и игровые меню — отдельные группы. На неизвестном вызове безопасная политика — исходная центральная композиция, с добавлением точной роли после разбора; не догадка по texture hash.

Просмотренный world geometry gate `801BC3D0` — проверка квадрата расстояния, а не горизонтального угла. Не увеличивать радиусы спавна/AI ради widescreen. Проверить связанные render-only отбрасывания/sky и static scissor во время реализации: текущий анализ не доказывает отсутствие всех иных отсечений. RT64 F3D cullDl в закреплённом коде TODO; нельзя обещать исправление путём одного изменения этого обработчика.

## Архитектура и владение кадром

Предлагаемые файлы: `src/widescreen.hpp/.cpp`, `tools/widescreen_patches.py`, локальный RT64 adapter по существующей схеме. Настройки — `port_settings.hpp/.cpp`, UI — `port_menu.cpp`, renderer configuration — `live_graphics.cpp`.

1. Layout snapshot с logical320×240, выбранными aspect/HUD, output geometry revision, overlay generation и per-pass role. Идентичность определять на guest build thread по точному overlay+callback/pass; переносить вместе с соответствующим display-list bank. Опора — существующий `frame_lights` snapshot/take, который уже решает проблему позднего чтения состояния другой сцены.
2. Extended display-list scopes для projection/rect/scissor/origin с восстановлением состояния. Один путь применяется к Original и всем Native/Manual кадрам; не прятать feature hooks внутри `UiFrameScope`, который включён лишь на дополнительных Native кадрах.
3. Преобразование центра: при высоте240 широкая логическая ширина `W=240*A`, боковой отступ `(W-320)/2`. При16:9 W≈426.667, поля≈53.333 с каждой стороны. Сохранять дробную точность до финальной упаковки команды; фазу тайлов вычислять относительно неизменного левого края исходной композиции, включая отрицательные координаты.
4. Готовые bitmap strips сохраняют порядок загрузок и palette/texel bounds. Для расширенного фона строить ограниченные полосы/блоки через существующую frame arena и extended rectangles; не расширять вслепую размеры texture loads или общий CPU bitmap clipping до выхода за ресурс.
5. Reset/смена overlay/resize: корректная инвалидизация временной разметки и frame ownership; сессионная подложка освобождается только после graphics barrier. Принятые texture retention и framebuffer/task synchronization не обходить.

## Производительность и framebuffer — обязательный связанный блок

`live_graphics.cpp:230` разрешает deferred readback лишь при RT64 Original. Просто включить Expand означает потерять принятый Native fast path. Просто убрать это условие тоже неправильно: `FramebufferReadback::materialize` требует scaleX==scaleY и abort при несоответствии, а wide workload задаёт scaleX=scaleY*aspectScale. Нынешний shader adapter в `prepare_rt64_sprite_edges.py` кодирует только равномерный scale, без horizontal origin.

Нужно описать отображение wide GPU target в логический guest320×240 для color и Z: для обычного расширенного3D исходной системе координат соответствует центральный участок, не верхний левый угол и не сжатие всего wide изображения. Сохранять фактический active rectangle/scale/origin последнего writer вместе с pending copy; allocation после resize может быть больше активной области. Добавить origin/scale metadata в readback adapter и shader constants, затем разрешить defer лишь для точно поддерживаемых target/pair.

CPU-dependent/offscreen/feedback effects требуют отдельного согласования: logical RAM остаётся исходного размера, нельзя менять VI_WIDTH или guest framebuffer stride на426. На неизвестном framebuffer path сохранять корректный eager fallback. Переключение aspect/resize сначала завершает нужные предыдущие копии с прежними метаданными. Широкий экран естественно добавляет GPU pixels, но не должен намеренно возвращать синхронный readback на каждый поддерживаемый Native frame. Фактический FPS подтвердит пользователь.

## Порядок реализации

1. Настройки/профили/сериализация, единый layout snapshot и переключение без рестарта.
2. Разделение generic RT64 aspect support и donor-only эвристик; явные pass roles, projection/scissor, readback coordinates с сохранением fast path.
3. Все world/auxiliary/menu perspective call sites и9 миниигр, включая многовидовые пути; фоновые модели и screen effects.
4. Точные bitmap policies: BC7 repeat160×120, BEC horizontal162; карта/иллюстрации по центру с подложкой; отдельные5 больших BMP и составные экраны по callers.
5. Полный HUD/диалоги/панели, overlays/fades, Original и Native/Manual, resize/fullscreen/reset/zone handoff. Сохранить исправления095 и предыдущие texture/map/menu fixes.
6. Статическая проверка границ/владения/вызовов, необходимая генерация, один инкрементальный Windows build после завершения целого блока. Игровую проверку делает пользователь. Документация результата и commit/push — после его проверки и команды.

Критерии пользовательской проверки: переключение4:3↔Fit и HUD independently;16:9/ультраширокое окно/resize; title/files/map/иллюстрации;3D с Original и Modern camera; HUD charge/meters/dialogue; инвентарь/оружие/персонаж; катсцены/fades; все9миниигр с участниками и split views; повторный вход в зоны и Reset; Original и Native/ManualFPS. Это список будущей ручной проверки, не пройденные тесты.

Неопределённости, остающиеся до реализации/ручного просмотра: скрытая геометрия у краёв сцен/меню, визуальный вид декоративной рамки карты, составные bitmap screens и редкие framebuffer effects. Архитектура предусматривает явные исключения для них, но статический анализ не может подтвердить их внешний вид.
