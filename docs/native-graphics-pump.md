# Запуск кадровых задач независимо от VI

2026-09-29. Продолжение native-frame-bridge.md, база f6684d8.

## Установленные изменения

Генерация v63 добавляет отдельное событие FFFFFF04 для очереди планировщика.
Оригинальные666/667/668/669 по-прежнему означают VI/SP/DP/PRENMI.
Перехват установлен перед800268EC после Receive. Он сохраняет регистры
планировщика, использует его s1 как OSSc* и возвращается к началу Receive.
При установленном флаге паузы801AA680 или после выхода из native-режима
специальное событие поглощается без запуска задач. Active проверяется через mutex
кадрового scheduler: поздний wake не ускоряет уже исходный Original-цикл.

Обработка использует оригинальную80026A28. В отдельной области вызова пропускаются
только запись счётчика retrace в80026A50 и рассылка клиентам с80026AEC.
Опустошение command queue, enqueue, выбор задач, запрос yield и launch выполняются
оригинальным кодом. Это не второй эмулированный VI и не другая реализация SDK scheduler.
Слова ROM у всех точек перехвата проверяются генератором.

Область такого вызова thread_local и восстанавливается RAII, включая исключение.
В pinned runtime каждому гостевому потоку соответствует отдельный host std::thread
(threads.cpp, osCreateThread). Поэтому yield через SDK не переводит чужой поток
в этот режим. Внутри pump сохраняется и приоритет уже готовой звуковой задачи;
звуковые тики дополнительно не создаются.

## Публикация предшествует пробуждению

Новый hook8002FF58 исполняется после возврата оригинального blocking SendMesg,
который публикует графическую задачу. Hook работает только внутри frame callback
FrameBridge: его область тоже thread_local. В Original дополнительных сообщений нет.
Перенос пробуждения перед публикацией позволил бы scheduler прочитать пустую очередь
и оставить кадр ждать следующего VI, поэтому порядок здесь существенен.

Оригинальная scheduler_init80027754 создаёт scheduler801A69D0, получает через
800268A0 адрес command queue (scheduler+78) и сохраняет его в80171584.
Перед пробуждением проверяется значение801A6A48. Event queue — scheduler+40,
то есть801A6A10. Это проверенные адреса третьей игры, не адреса Dora64.

Само пробуждение ставится в существующую внешнюю очередь runtime с requeue=true
и проверкой результата host enqueue. Оно не блокирует игровой поток на заполненной
event queue: scheduler может в это время ждать освобождения очереди игровых completion.
Добавлять второй blocking SendMesg между этими потоками было бы лишним условием
взаимной блокировки. При full event queue запрос сохраняется до освобождения места.
Нехватка host-памяти не скрывается: начальный отказ и потеря повторной постановки
native wake приводят к bad_alloc. Это не искусственный предел времени/числа кадров.

Специальное событие не содержит pointer или token кадра: оно только просит
проверить уже опубликованную очередь задач. Повторное событие не повторяет enqueue
задачи. Запрос создаётся на фактическую native-публикацию, а не на каждое срабатывание
будущего таймера. При сбросе его удаляет существующая очистка внешних очередей.

## Проверки

tools/check_native_graphics_pump.py компилирует11 оригинальных функций из v63,
включая thread/retrace/enqueue/select/launch/SP/DP/task-complete и graphics-task-submit.
Используется настоящая adapted mesgqueue.cpp. Искусственная RAM получает только
необходимую jump table из ROM в ignored build-local; игровые данные в Git не записываются.
Аппаратные SDK endpoints и переключение guest threads заменены проверяемыми stubs.

Проверены цепочка native frame callback → исходная публикация → внешняя очередь →
оригинальный scheduler, полностью заполненная event queue, отсутствие дополнительных
VI-счётчиков/рассылки двум клиентам, приоритет audio и yield уже занятого SP,
отдельные SP/DP completion, ровно один запуск при повторном wake, исходная пауза,
сохранение регистров и независимость thread_local между host-потоками.
Обычное событие VI по-прежнему увеличивает исходные счётчики и уведомляет клиентов.

ASan/LSan проходят. Повторно проверены frame-light snapshots в изменённой функции
публикации и FrameBridge (ASan/LSan, TSan с прежним ограничением atomic_thread_fence
в сторонней concurrentqueue). Ни игровое окно, ни GPU не запускались.

## Уточнение фактического пути показа третьей игры

Ранее native-frame-bridge.md называл уведомление CPU overlay будущей необходимой
границей. Уточнение: в pinned runtime действительно есть
ultramodern_notify_cpu_framebuffer_write, но вызовов в src, генераторе и generated
коде третьей игры не найдено. Комментарий внутри этой функции описывает Dora64,
а не установленный протокол третьей игры. Нельзя считать его существующим hook Dora64-3.

Текущий live frontend не задаёт PresentEarly. Pinned EnhancementConfiguration
по умолчанию использует SkipBuffering. Показ запрашивается periodic VI-путём;
при его подготовке runtime берёт прежние regs и затем вызывает update_vi.
Следовательно, снятие ограничения только у scheduler не создаёт самостоятельный
показ каждого нового framebuffer.

State::updateScreen читает CPU framebuffer, проверяет его изменения и копирует
данные в owned present.storage до передачи на другой поток. Но адрес изображения
вычисляется из VI origin/width/scales, а не просто из OSScTask+0C. В update_vi origin
равен physical framebuffer + field origin с учётом repeatline; black меняет hStart.
Для native-показа нужен корректный снимок этих параметров для соответствующего кадра.
Подмена одного указателя или вызов донорского notify с текущими regs недостаточны.

У третьей игры подтверждена CPU-копия800271B0 на переходах; она уже защищена
graphics_rdram_mutex. Это не доказательство CPU-отрисовки всех меню/текста.
Существующую защиту RAM, света и отложенного освобождения необходимо сохранить.

## Что остаётся до включения

Framebuffer-ready80026CEC **по-прежнему требует current==next**, что отдельно
проверено стендом. Без согласованного native present с обходом только для принадлежащих
ему кадров этот gate продолжит связывать последующие задачи с60Hz VI.
Он не удалён ради красивого числа FPS.

Нужно связать реальные подтверждения GuestTask/HostRead, снимок правильного VI/
framebuffer и окончание чтений updateScreen. Guest completion отправляется до SwapBuffer;
освобождение банка прямо перед SendMesg было бы преждевременным, поскольку scheduler
ещё читает task+0C. Затем — таймер с корректным shutdown/reset, безопасные границы
Original/Manual и включение первой проверенной2D-сцены с новыми elapsed-time обновлениями.

Native Manual пока не активирован. Нового пользовательского EXE в этой итерации нет;
последний переданный остаётся test-024. Original сохраняет исходное поведение.
