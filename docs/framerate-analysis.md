# Частота кадров Doraemon 3: анализ после test-024

Дата: 2026-09-29. Пользователь наблюдает20FPS в Original, дрожание полигонов на
стыках при60FPS и непостоянное достижение целевой частоты. Запрошен только анализ.
Игровой код, генераторы, зависимости, настройки, ROM и EXE не менялись; игру
агент не запускал. База исходников: main1d2c7f6, test-024.

## Что проверено по оригинальному ROM

ROM N3DJ rev0 сверён с rom.lock.json. Адреса ниже принадлежат третьей игре.
Исследованы исходные слова ROM и соответствующие generated-функции, а не только
старые подписи карты. В research/framerate-static-analysis.json — хэши восьми
рассмотренных тел и24 найденных прямых записи делителя в известных compiled-телах.
Это не доказательство отсутствия косвенных записей во всём ROM.

| Адрес/функция | Проверенное назначение |
|---|---|
| 801A39DC | Порог числа retrace для игрового обновления |
| 801AC694 | Счётчик retrace; увеличивается scheduler по80026954–8002696C |
| 800307F8 / 80030810–80030838 | Сравнение счётчика с порогом; при достижении обнуляет счётчик и801A48C0 |
| 801BB94C в.scene1 | Инициализация основного игрового блока записывает3 в801A39DC |
| 801C0198 в.scene34 | Меню/начальная сцена также записывает3 |
| 80027B08 / 8004341C | Начальная resident-логика записывает2 |
| 801B5104 / 801B71DC в.startup_scene | Ещё две записи2 |
| 8002787C / 80027970–800279D4 | Построение кадра допускается при outstanding<2 и801A48C0==0 |
| 800279F4 | После построения закрывает разрешение кадра через801A48C0=1 |
| 80030860 | Вызывает800281B8 с фазой0: обновления игровых процессов |
| 8002FFEC | Построитель8002FF64 вызывает800281B8 с фазой1: render-процессы |

Всего обнаружены20 прямых записей3 и4 записи2. По проверенной цепочке создания
scheduler osViSetEvent получает retraceCount=1; далее деление выполняет сама игра.
Для NTSC это номинально60/3≈20 или60/2≈30 обновлений в секунду при достаточной
производительности. Это программный порог, а не просто нехватка мощности N64.
Точная частота зависит от VI-тайминга и готовности кадров;20FPS не следует считать
универсальным режимом всех сцен. Старое описание every2 retraces в startup.json
отражает только начальный режим, а не основной gameplay; этот input генератора
в рамках анализа не редактировался.

## Почему нельзя просто заменить3 на1

Порог разрешает не только рисование, но и игровые обновления:

- Process dispatcher800281B8 уменьшает целочисленный sleep-счётчик на1 за вызов
  нужной фазы (80028218–8002822C). При вызове в три раза чаще ожидания сокращаются.
- Fade tick80028948 прибавляет фиксированный знаковый шаг к альфе, без умножения
  на elapsed time. Он вызывается за тем же порогом: фейды ускорятся.
- Там же находятся latch/reset ввода, rumble, pak state machine и sound-event cleanup.
  Их частоты нельзя менять общим коэффициентом без анализа. Аудиосинтез имеет
  отдельные VI/sample-driven процессы, поэтому ускорение игрового тика может
  рассогласовать музыку с игровыми событиями, а не просто ускорить весь звук.
- Переменные COUNT в800331F8/8003321C измеряют длительность обработки. Сам факт
  такого измерения не доказывает, что физика и анимации используют delta time.

Для физики/анимаций всех персонажей и миниигр исчерпывающей карты временных
зависимостей ещё нет. Поэтому утверждать, что достаточно поделить скорости на3,
нельзя: отдельно рассматриваются ускорения, дискретные таймеры, столкновения,
ввод, камера, события и переходы. Сценам исходных30FPS нужен иной коэффициент.

## Что сейчас делает Frame rate

В test-024 меняется RT64::UserConfiguration.refreshRate/refreshRateTarget.
Guest VI, делитель801A39DC и игровой scheduler не меняются. Значение60 сейчас
означает цель вывода RT64, а не60 полных обновлений оригинальной игры.

В pinned RT64 WorkloadQueue::threadLoop выполняется GameFrame::match и создаются
дополнительные кадры, только когда targetRate>viOriginalRate, workload не paused
и найден подходящий interpolation framebuffer. PresentQueue отдельно запрещает
использовать интерполированные targets для CPU framebuffer writes. При этих
условиях возврат к меньшему числу кадров допустим самим алгоритмом, даже без
падения производительности GPU. Не каждый недобор FPS означает новый cap.

Счётчик меню считает вызовы RT64 draw hook; это не profiler времени CPU/GPU,
не число игровых update и не доказательство скорости сканирования монитора.
В двух последних просмотренных логах test-024 используется D3D12. Полных
frame-time, matching и GPU timing данных в этих логах нет; причину недобора
целевого FPS по ним установить нельзя.

## Дрожание стыков: гипотеза и её границы

Основная гипотеза — неодинаковая интерполяция соседних частей геометрии из-за
автоматического сопоставления matrices/draw calls или смены порядка/видимости.
Она согласуется с наблюдением пользователя: артефакт появляется при повышении FPS.
Это ещё не доказанный диагноз конкретного стыка: кадр/пара workloads не захвачены.
Также остаются возможными depth precision/z-fighting, округление матриц/вершин,
смешение частот деформации и трансформаций или ранее невыявленный срок жизни данных.

В текущем адаптере Dora64-3 нет game-specific gEX matrix IDs / transform groups.
RT64 по умолчанию использует G_EX_ID_AUTO; position/rotation/scale и другие
компоненты AUTO, vertexInterpolation=SKIP. У третьей игры подтверждена CPU morph
анимация парных vertex-буферов (80038BC8/80038D58/8003931C), поэтому плавное движение
матрицы ещё не означает плавную деформацию модели. К дрожанию именно статического
стыка это пока не привязано; это отдельное ограничение текущего HFR-пути.

В просмотренном frontend первой игры используются снимки кадровых ресурсов,
callback модельных матриц и адаптер перенесённого model pool. Это адресно-зависимые
исправления памяти, а не готовая универсальная разметка интерполяции Doraemon3.
Проверенная плавность Dora64 не является доказательством совместимости этих сцен.

## Оценка путей к60

| Путь | Что потребуется | Оценка |
|---|---|---|
| Игровая логика20/30 + корректный вывод60 | Явная идентичность камеры/объектов/частей сцены, согласованные transform groups, обработка cut/появления/исчезновения; выборочная интерполяция динамических вершин | Наиболее ограниченный по влиянию на механику путь; автоматическая интерполяция пока недостаточно надёжна |
| Отделить native render60 от update20/30 | Использовать разделение phase0/phase1, проверить побочные изменения render callbacks; строить промежуточное visual state | Кандидат архитектуры. Просто рисовать неизменное состояние60 раз не даст60 фаз движения |
| Реальные update+render60 | Делитель1 и полный пересчёт временных зависимостей разных сцен, физики, камеры, анимации, скриптов и ввода | Техническая точка входа найдена; объём значительно больше. Корректность не обеспечивается заменой одного значения |

Предложение для следующего разрешённого этапа: взять один воспроизводимый стык,
разделить original/generated кадры и проверить camera/world-transform matching;
параллельно составить карту side effects phase1 и временных зависимостей одного
основного gameplay-состояния. Это позволит выбрать между управляемой интерполяцией
и native-render60 на фактах. До этого не менять глобальный делитель и не объявлять
режим60 исправленным. В этом анализе никакой из путей не реализован.
