# Этапы до рабочего порта

## 0. Исследовательская основа — начата, есть проверяемый результат

ROM зафиксирован, общая база изучена, зависимости изолированы. Работают
boot-probe и оригинальный декодер в отдельном окружении. Есть частичная карта
загрузчиков, формат сжатия и воспроизводимые отчёты.

## 1. Резидентный CPU-код и загрузка оверлеев

Построить карту функций для resident с разделением CPU/RSP/data; установить
SDK-символы по инструкциям и call sites, включая thread/message/PI/VI/SI/EEPROM.
Не выдавать эвристические prologue/jal кандидаты за проверенную symbol map.
Выполнено в диагностическом Linux runtime: bootproc 0x80027414 → idle
0x800276B0 → main 0x80027A88; работает поток scheduler 0x800268A8.
Текущая граница: 0x80051B88 внутри оригинального конструктора синтезатора.
Инициализировать osTvType для NTSC: иначе в bootproc есть бесконечные ветви.

Учесть подтверждённую границу чтения 0x3FF/0x400; предпочесть минимальное
обоснованное решение в адаптере третьей игры или общий PI fix с отдельной
проверкой. Не менять зависимости первого Dora64.

Для 14 известных и последующих загрузок установить исполняемые границы,
общие/взаимоисключающие секции, таблицы косвенных вызовов, BSS/relocations.
Зарегистрировать активные функции при DMA, включая callback targets.
Критерий этапа: boot/main исполняются под runtime без пустых заглушек игровых
функций, неизвестные вызовы завершаются диагностикой с ROM/VRAM/section.

## 2. Первый кадр, ввод, звук — ближайшая игровая цель

Минимальный frontend с новым app ID и отдельными настройками/сохранениями,
исходными 4:3, скоростью/таймингом и оригинальным управлением.
Подключить исправленные runtime/RT64, но заново определить память задач и
срок её жизни. Зафиксировать фактические OSTask type, ucode text/data hashes,
VI и display-list addresses. Не отправлять нераспознанный ucode как aspMain первой игры.

Аудиомикрокод локализован независимо: ROM 0x3DAF0, размер 0xE20,
16 indirect targets прочитаны из ROM. RSP сгенерирован и компилируется отдельно.
Следующее: дойти до реального OSTask, проверить его диапазоны и подключить RSP.
Убедиться, что реальный PCM поступает в SDL при исходном темпе.
Ввод: сначала кнопки/стик через стандартный N64 controller API.
Критерий: пользователь видит первый кадр, может пройти меню/войти в игровой
эпизод, слышит звук; цикл устойчив, unknown calls/ucodes не замалчиваются.

## 3. Сохранения и устойчивый исходный цикл

Проверить EEPROM 16 Кбит по коду, game slots/checksum/commit points.
После нормального save/load — безопасное autosave и backup с атомарной записью.
Проверить pause/focus/background/resume/reset, завершение GPU/audio работ,
отключение контроллера. Сборки Windows/Linux, затем Android package/ROM picker.
Установку и прохождение выполняет пользователь. Исправлять конкретные причины.

## 4. Изображение и управление

Сначала правильные widescreen projection/culling/HUD/2D/cutscenes; затем
интерполяция отображения с исходной частотой game updates и стабильными IDs
матриц/объектов. Камеру разбирать отдельно: ownership/locks, collision,
camera-relative movement. Сохранить Original mode.
LOD/draw distance вводить только после определения потоковой загрузки,
пулов и существования соответствующих механизмов в третьей игре.

## 5. Port menu и Android touch

Профили Modern/Original только для готовых опций; масштабирование по output.
Клавиатура/gamepad/rebind. Затем перенос общего touch ownership/editor/JSON,
новая раскладка, multitouch, camera swipes, hide/reveal и lifecycle release.
Контекст диалога/камеры получать из новых подтверждённых сигналов.

## 6. Локализация и необязательные читы

Каталог текста/кодировки/шрифтов/динамических подстановок и необходимых текстур
получать из третьей игры; японский оригинал оставить доступным. Отдельно RU/EN,
переполнение строк и текстовые окна. Не переносить сюжет/ресурсы первой игры.
Читы выбирать по реальным механикам и новым адресам, все выключены по умолчанию.

## 7. Упаковка и воспроизводимость

Чистая сборка из pinned sources + пользовательского ROM, отдельные платформенные
директории, строгая проверка ROM, отсутствие игровых данных в архиве исходников,
инструкции RU/EN и перечень выполненных проверок. Android signing key отдельно,
публикация только после команды пользователя.

Не обещать равные FPS, сроки полного порта или универсальную совместимость
движка. Этапы завершаются по проверяемому поведению, а не по факту компиляции.
