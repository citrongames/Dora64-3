# Протокол настоящих кадров и первая сквозная проверка 2D

2026-09-29, продолжение native-framerate.md. База: main 3a9b686.

## Реализовано

`src/native_frame_scheduler.*` связывает ManualClock с двумя банками задач.
Это код протокола и его проверка, **ещё не подключённый обработчик живой игровой
очереди**. Существующие test-024, Original и поведение Manual не изменены.

Порядок: request → enqueue → receive/reserve → build → publish → два completion.
Для таймера, игрового потока и обработчиков завершения предусмотрена защита mutex.
Под mutex нет вызовов внешних обработчиков, гостевого SDK или ожидания GPU.

- Одновременно ожидает доставки не более одного нового запроса кадра.
- Кадровое время расходуется при принятии запроса игровым потоком, не при его
  постановке в очередь. Отказ enqueue не теряет время.
- При занятости следующего банка нет новых запросов и нет просроченного deadline
  для активного опроса. Таймер должен проснуться от completion/изменения режима.
- У каждого банка собственные epoch/serial, стадии Building/Published и два
  независимых подтверждения GuestTask/HostRead. Одного подтверждения недостаточно.
  Поздний повтор старого completion не освобождает уже переиспользованный банк.
- Leave прекращает выдачу запросов, но сохраняет владение незавершёнными задачами.
  Enter допускается после их завершения и явного подтверждения адаптером, что
  исходные задачи тоже закончены и достигнута безопасная граница игрового тика.
  Сам новый реестр ничего не знает о ранее выданных Original-задачах.
- Изменение FPS отменяет старый запрос, сохраняя накопленное время. Смена сцены
  через leave/enter создаёт новое поколение и не переносит время загрузки в сцену.
- Все структуры имеют постоянный размер; нет очереди на каждый пропущенный кадр,
  контейнеров с неограниченным ростом, лимита длительности игры или stop по счётчику.

HostRead — контракт с будущим адаптером, а не название уже существующего сигнала.
Он должен означать завершение всех относящихся к банку чтений гостевой памяти
либо владение корректным снимком. Нельзя автоматически подставить parse completion
вместо готовности GPU или окончания более позднего CPU framebuffer чтения.
Существующие graphics_rdram_mutex, immutable snapshots, light/retirement guards
сохраняются. Новая проверка протокола не доказывает корректность их будущего соединения.

## Доставка через 32-битный OSMesg

WakeMailbox хранит неизменяемую копию epoch/serial до чтения соответствующего
сообщения. Нельзя заменить её новой после смены сцены: старое сообщение тогда
выполнит новый запрос (ABA). Новая постановка ждёт освобождения единственной ячейки.
При реальном отказе enqueue отменяется только соответствующий token.

Зарезервировано значение 0xFFFFFF03. Это **не гостевой указатель**. Будущий адаптер
должен перехватывать его только в игровой очереди801A99E0 после Receive и ДО
разыменования сообщения, в том числе после возврата в Original. Даже пустое/устаревшее
специальное сообщение нужно поглотить, не передавать оригинальному `lh`.
Обычные сообщения mailbox не потребляет. Источник обязан посылать ровно одно сообщение
на prepare, без дублирования/повторной постановки после успешной отправки.
Сейчас это значение никуда в настоящем runtime не отправляется.

## Что проверено оригинальными функциями

`tools/check_native_frame_scheduler.py --generated build-local/startup-v61`
подтверждает generation receipt, извлекает четыре original тела в build-local,
собирает их на синтетической RAM. Внешние SDK endpoints заменены проверяемыми stubs.

80026CEC действительно запрещает готовность при current framebuffer != next.
80026D40 не отправляет completion, пока установлены ресурсные биты0/1. При graphics
flags60 и type1 порядок — SendMesg, при необходимости ViBlack(false), затем SwapBuffer.
То есть получение task completion и защёлкивание framebuffer на VI — разные вещи.
Для audio type2 swap не вызывается. Это проверено выполнением оригинальных тел.

Дополнительно выполнен полный синтетический проход:

Manual deadline → 32-битное сообщение/token → резерв банка → Fade(elapsed) → запись
альфы → **оригинальные800289D8/80028688** строят новый2D display list → публикация →
синтетические guest/host completion.

На60/73/144/165/360FPS число построенных списков за фейд — соответственно48/59/116/132/288.
Каждый список содержит вычисленную для этого момента альфу; дополнительных различных
значений больше исходных16. Соседний банк не меняется. Завершение приходится на
первый кадр не раньше0,8 секунды, с погрешностью дискретизации менее одного нового
кадра. Это не RT64 interpolation и не многократная отправка одного неизменного списка.
Однако это **не полная сцена, не визуальная проверка и не игровой HFR-режим**.

ASan/LSan и отдельный TSan прошли, включая2000 кадров с параллельными подтверждениями.
Проверены разные порядки completion, повторные и старые токены, заполнение двух банков,
отказ enqueue, переключение сцены/частоты, отсутствие запросов в неактивном режиме.
Сборки Linux/Windows проверяются отдельно; Android в этой итерации не проверяется.

## Новые точки подключения и границы аудита

- 800278F4: первая инструкция после блокирующего Receive игровой очереди; сообщение
  лежит в sp+10. До80027918 (`lh` по сообщению) нужен отдельный host-event dispatch.
  Нельзя просто послать дополнительный retrace:80027938/40 тогда ускорят lifetime ticks.
- 80026904: разбор scheduler-сообщения после Receive. Коды666..669 уже принадлежат
  VI/SP/DP/PRENMI. Новое графическое событие не должно выполнять ветвь666 с инкрементом
  retrace и рассылкой клиентам/звуку.
- 80026A28 одновременно опустошает scheduler command queue, запускает задачи,
  увеличивает retrace count и рассылает клиентам события. Нужна отдельная графическая
  ветвь pump без этих VI-побочных действий; копировать вызов целиком нельзя.
- Source runtime `ultramodern_notify_cpu_framebuffer_write` берёт текущие VI regs.
  Нативная частота выше60 требует согласования фактического framebuffer и полного
  CPU overlay до его публикации, а не только обхода80026CEC.

Уточнена первая небольшая2D-сцена: scene34 с update801C0088/draw801C012C — экран
центрированного изображения либо сообщения о контроллере, не вся система главного меню.
801C0088 обслуживает repeat ввода и целочисленные таймеры801C68CC/801C68D0.
Ветка801BFF24 строит центрированное изображение через texture-info/rect helpers;
ветка801BFE80 вызывает common text/frame helpers. Полный аудит их побочных эффектов
ещё не завершён. Нельзя распространять проверку одного фейда на всю сцену.

У другого меню32 draw801BFC44 записывает801C68AC из801C673C после рисования.
Это конкретный пример записи игрового состояния в render callback: дополнительные
вызовы phase1 требуют аудита смысла этой записи и читателей. Глобально повторять
все phase1 без такого аудита нельзя.
