# Нативный старт: первый audio RSP и графическая задача

Диагностический frontend работает в Linux x86-64 / WSL2 с GCC 15.2,
RelWithDebInfo и закреплённым N64ModernRuntime из отдельного build-deps.
Окна, RT64 renderer и аудиоустройства пока нет. Библиотеки и pins не менялись.

## Подтверждено исполнением

- Оригинальные entry → bootproc → idle → main и scheduler выполняются нативно.
- Пройдены начальные VI/SI/controller queues, task buffers, игровые пулы и
  таблица процессов. Main вошёл в цикл сообщений 8002787C.
- Контроллеры отключены; реальный ввод и ветви подключённого Controller Pak
  не проверены. Сохранения отключены.
- DMA wrapper 8002730C использует настоящий osEPiStartDma и очередь завершения.
  ROM FA1FA0 → RAM 800DD8F0, 1C760 байт; ROM FBE700 → RAM 800FADE0, 2580 байт.
  Оба диапазона совпали с ROM побайтно до оригинальной релокации банков.
- Завершён конструктор синтезатора: voice pool, фильтры, эффект, DMA pool,
  player callback. Вызван osAiSetFrequency(22050).
- Запущен audio thread id3, entry 8004E044. Он дождался retrace, построил
  audio ABI commands и отправил настоящую задачу через 8004DD4C.
- Планировщик через исходную функцию 80026E24 и SDK osSpTaskLoad/osSpTaskStartGo
  передал задачу в runtime. В v15 RSP обработал 0x9A0 байт команд по 800C0CD0,
  проверил загруженный текст и вернул штатный Broke(1). Это одна задача,
  ещё не проверка PCM, музыки, доставки SP completion или непрерывного звука.
- В более раннем v13 первая graphics task дошла до диагностического renderer:
  ucode=80063510, declared size=1000, display list=80120638, bytes=30 (hex).
  Renderer остановился до обработки display list; отрисованного кадра нет.

Доказательства: research/startup-check.json (сборка с audio RSP) и
research/graphics-task-check.json (предыдущая сборка). Это разные executable;
журналы и двоичные файлы остаются в build-local.

## Функции и границы

recomp/startup.json: 131 отобранная оригинальная функция, 38 SDK entries и
15 явно установленных indirect targets. Генератор создал 60 fail-stop границ:
прямые JAL обнаруживаются автоматически, найденные callback targets — явно.
Пустых успешных заглушек нет. Названия dora3_* обозначают исследованные роли,
не оригинальные символы. Просмотр тела и прохождение одной ветви не означают
проверки всех ветвей.

V15 остановился на 800331F8 в следующем обновлении main. В других запусках
первой может стать графическая граница или SP completion 80026B28: порядок
зависит от host scheduling. Это диагностический срез, не устойчивый игровой цикл.
При fail-stop вызывающий поток больше не исполняет игру; уже отправленной
аудиозадаче даётся до 250 мс на завершение. Это диагностическая задержка,
не игровой тайминг и не доказательство завершения всей очереди.

Resident section содержит ROM 1000..59E80, включая данные; компилируются только
перечисленные функции. Полные таблицы косвенных вызовов и оверлеев не покрыты.
Предварительный disassembly до ROM 3E910 включал RSP; начало RSP boot теперь
установлено как 3DA20. Автоматические function boundaries остаются кандидатами.

## Звуковой RSP

Указатели найдены независимо в audio thread8004E044 и task builder8004DD4C;
проверены RSP boot и таблица переходов. Адреса первой игры не переносились.

| Роль | ROM | VRAM / IMEM | Размер |
|---|---|---|---|
| RSP boot | 0x3DA20 | 0x80062620 | 0xD0 |
| Audio text | 0x3DAF0 | 0x800626F0 / 0x1080 | 0xE20 инструкций |
| Audio data | 0x53F40 | 0x80078B40 | задача объявляет 0x800 |

SHA-256 audio text:
14e3b245e8cd4e0bdf4cbb864af82d1ccba6d3d3ff33f73cb52c5821a76f30fc.
Текст побайтно совпал с audio text первой игры после независимого определения
местоположения. Это не доказывает совпадение CPU-аудиодвижков.
16 u16 dispatch targets читаются из audio data +0x10.

Живая задача объявляет ucode_size=0x1000; инструкций 0xE20. Нельзя расширять
компиляцию на соседние байты из-за размера OSTask. Data_size=0x800 не доказывает
границу всей связанной data-секции. Pinned runtime загружает 0xF80 data bytes
в DMEM независимо от declared size; это поведение пока не менялось.

CMake проверяет CPU/RSP generation receipts и связывает оба результата с frontend.
RSP выбирается только для type2 с установленными адресами/размерами и допустимым
command list. Загруженные text bytes сравниваются с ROM перед исполнением.
Broke подтверждает только наблюдавшийся startup list; активные ADPCM/raw voices
и sample DMA callbacks ещё защищены остановками. PCM не проверен.

## Следующая работа

1. Продолжить main от 800331F8, SP completion от 80026B28 и начальный игровой
   процесс 800433D8, не обходя неизвестные функции.
2. Разрешить PI случай 0x3FF/0x400 при реальном сжатом чтении и зарегистрировать
   активные оверлеи. Чётные банковые DMA не проверяют этот случай.
3. Подключить RT64, отдельно установив сроки жизни task/display-list памяти;
   получить видимый кадр и исходный ввод.
4. Проверить активные голоса, завершения задач, PCM и вывод в SDL с исходным
   темпом. Затем Windows/Android frontend; прежние проверки — лишь boot-probe.

## Источники и воспроизводимость

- ROM пользователя, проверяемый по recomp/rom.lock.json.
- Закреплённые runtime/N64Recomp: dependencies.lock.json и tools/n64recomp/lock.json.
- [ultralib reference](https://github.com/decompals/ultralib/tree/e24c836796df4bf520ff8b11a5c9d2cea3a66cbd),
  commit e24c836796df4bf520ff8b11a5c9d2cea3a66cbd, сверка API/структур.
- [spimdisasm](https://github.com/Decompollaborate/spimdisasm) 1.42.4,
  rabbitizer 1.16.2 — подсказки анализа, не обязательная часть сборки.

Команды — в reproduction.md. ROM, generated C/RSP, дизассемблирование, state
и извлечённые ресурсы нельзя включать в исходные или релизные архивы.
