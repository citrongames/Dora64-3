# Динамические вершины и граница чтения RT64

Продолжение аудита после test-018. Игровой код, runtime и зависимости не менялись;
новый EXE для этих исследовательских изменений не требуется. Проверены оригинальные
инструкции N3DJ rev0 и закреплённые исходники RT64. Бинарные исходные данные не публикуются.

## Восстановленная цепочка одной группы ресурсов

| Шаг | Проверенные адреса и поля |
|---|---|
| Создание |80038BC8 выделяет два буфера по object[+30] ×16 байт, копирует исходник object[+20], сохраняет адреса в +6C/+70 |
| Изменение |80038D58 берёт current object из80082724, индекс банка из801A9544 и пишет координаты/нормали выбранного буфера; второй банк не трогает |
| Анимационный вызов |8003931C проверяет наличие +6C и вызывает80038D58 с данными выбранной анимации |
| Публикация ссылки |8003AC14 строит segment command DB06: при наличии выбранного +6C/+70 указывает на него, иначе на исходник +20. Выбор сегмента задаётся object[+40] |
| Удаление |80038C58 передаёт обе непустые ссылки в80038B10, затем обнуляет +6C/+70 |
| Отложенный free |80038B4C после16 ticks вызывает80033C50; free/coalesce80033BA4 меняет метаданные heap, а повторное выделение может перезаписать payload |

Все прямые вызовы80038B10 в известных4778 телах — две инструкции внутри80038C58.
Последняя имеет callers8002A5A4 (объект из массива+74) и8003B77C (удаление модели).
Это значительно сужает назначение реестра, но не исключает косвенных вызовов.
Наличие двух буферов объясняет безопасность смены банка при обычной анимации;
не объясняет безопасность уничтожения модели, пока её DL ещё ждёт разбора.

## Компонентная проверка оригинального кода

check_paired_vertices.py извлекает пять полных generated-функций из проверенной
generation receipt:80038BC8,80038D58,80038C58,80038B10,80038B4C. Allocation/free
endpoints подменены только на синтетические адреса и учёт обращений. Реальный
allocator этим стендом не проверяется (его отдельная проверка была в test-017).

Проверено: две отдельные копии исходника; изменение выбранного банка и сохранность
другого; неизменность второго vertex, texture coordinates и alpha в рассмотренном
morph; обнуление owner pointers после регистрации; free после16 ticks при pending=2.
Отдельный граничный случай:51 последовательное создание/удаление пары без ticks
даёт102 allocation и100 free. Указатели владельца на две потерянные записи уже
обнулены. Это более конкретное подтверждение механизма возможной утечки, чем
прежний вызов enqueue101 раз. Частота/достижимость такого расписания в игре неизвестна.
ASan/LSan: exit0. Санитайзер не считает гостевые потерянные указатели host-утечкой.

## Где заканчивается чтение источника в RT64

| Потребитель | Граница владения |
|---|---|
| F3DEX2 vertices |RSP::setVertex копирует Vertex в собственный vertices[], затем преобразует данные в workload |
| Обычные текстуры/TLUT |loadTile/loadBlock/loadTLUT читают RDRAM в TMEM. Сохранённые LoadOperations могут повторить чтение во время FullSync; конец первого load недостаточен |
| Upload thread |TextureCache::queueGPUUploadTMEM создаёт отдельный vector bytesTMEM до помещения в uploadQueue. Поток загрузки не сохраняет исходный указатель на гостевые texture bytes |
| FullSync |State::fullSyncFramebufferPairTiles выполняет повторные LoadOperations и ставит owned texture copies. Это происходит внутри синхронного send_dl |
| Present |State::updateScreen копирует RAM в present.storage; отдельный present consumer использует эту копию для вывода из памяти |
| Texture hash bookkeeping |После eviction State вызывает TextureManager::removeHashes; hashSet не является безусловным вечным списком всех увиденных текстур |

Следствие для рассмотренного обычного пути: нужна граница завершённого send_dl
конкретной опубликованной задачи, включая FullSync. Ожидание всего последующего
GPU/present не нужно для уже скопированных вершин/обычных текстур. Это не общая
гарантия для framebuffer feedback, нестандартного microcode или всех видов данных.
SP/DP уже выдаются после send_dl, но resource timers по-прежнему могут сработать
до него: событие завершения и политика освобождения — разные части протокола.

## Уточнение CPU framebuffer

8002F594 только формирует depth fill DL; название «clear» не означает CPU stores
в пиксели.800314E4 устанавливает VI mode, bank framebuffer pointers и heap;
80031588 задаёт исходные указатели и размеры. Эти три функции не требуют
новых блокировок вокруг записи изображения. Прежняя CPU-копия800271B0 остаётся
защищённой. Полный interprocedural анализ других pixel writers не завершён.

## Что остаётся до исправления retirement

Нужно связать конкретные retiring buffers с последовательностью опубликованных
и уже разобранных задач. Проверка «outstanding==0» при каждом tick недостаточна:
новые кадры могут поддерживать очередь ненулевой постоянно. Ожидание на игровом
потоке тоже нельзя добавлять без анализа scheduler — ещё не переданную host-очереди
задачу должен сначала запустить гостевой scheduler. Переполнение нельзя исправлять
немедленным free: это сокращает исходную задержку и может повредить ещё читаемые вершины.
Отдельно требуется проверить очистку при смене heap/сцены и повторное получение ресурса.
