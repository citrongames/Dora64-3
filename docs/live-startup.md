# Живой RT64: первый экран scene34

## Проверено 2026-09-27

Исследовательский Linux frontend в WSLg/Vulkan на RTX2060 исполнил оригинальную
инициализацию, обновление и отрисовку стартовой scene0x22 (34). После двух
списков настройки RT64 обработал30 содержательных graphics tasks: рамку,
три строки текста и исходную заливку перехода. На32-й задаче запуск намеренно
заканчивается кодом78; неизвестные функции на этом пути не вызваны.
Пользователь сообщил, что видел просьбу подключить контроллер в окне.
Это наблюдение пользователя, не автоматическая проверка пикселей.

Контроллеры пока отключены в frontend. Bit0 маски801A48B4 равен0, поэтому
801C0184 устанавливает801C68C4=1, draw801C012C выбирает801BFE80. Отсюда
экран предупреждения; условие игры не обходится. Ветка с центральной картинкой
801BFF24 рекомпилирована, но в этом запуске не исполнялась.

Состав:245 оригинальных функций (227 resident +18 overlay),43 SDK mappings,
18 установленных indirect targets,68 явных fail-stop границ для других путей.
Новый код взят из ROM третьей игры; адреса/пулы/патчи первой не переносились.
Результат: [research/live-startup-check.json](../research/live-startup-check.json).
Предыдущие границы v24/v31..v35 сохранены в research/history.

89 настоящих audio RSP tasks завершились; PCM callback получил45568 стереокадров
с нулевыми отсчётами. PCM измеряется и отбрасывается. Это не слышимый звук и
не проверка активных аудиоголосов. EEPROM16k startup прочитал три пустых слота
и подготовил RAM; запись/повторная загрузка непустого сохранения не проверены.

## Секции и регистрация кода

| Секция | ROM | RAM | Размер |
| --- | --- | --- | --- |
| resident | 0x1000 | 0x80025C00 | 0x58E80 |
| common scene | 0x5E400 | 0x801B3770 | 0x51C0 |
| scene34 | 0x635C0 | 0x801B8ED0 | 0xD490 |

Генератор использует отдельную ROM/VRAM дельту каждой секции. Например,
801C0184 соответствует ROM6A874. Перекрытия секций, выход функций за границы
и неверные ROM ranges останавливают генерацию. Взаимоисключающие оверлеи
с одинаковой VRAM пока не поддержаны; нужен отдельный namespace/план регистрации.

Runtime init автоматически регистрирует секции внутри boot copy1MiB относительно
entrypoint. Для оверлеев это неверные временные адреса. Entry hook удаляет эти
aliases до игрового кода. После каждой настоящей overlay DMA проверяются все
байты, затем вызывается load_overlays с правильной RAM. Вход в незагруженную
overlay function завершает запуск85. Scene clear80043390 и перекрывающая DMA
снимают прежнюю регистрацию. Повторная смена сцен ещё не проверена исполнением.
Исходники runtime при этом не изменяются.

Инициализатор801C0184 создаёт процессы801C0088/801C012C, очищает собственные
пулы и загружает ресурсы через оригинальные allocator/DMA/LZSS. Значение
801C6A30 — начальный указатель выделения памяти, не таблица ресурсов.

## Исправление чтения сжатого потока

Полный refill80034000 запрашивает3FF байт, но читает400. Runtime копирует
запрошенную длину буквально. На крупном ресурсе ROM491240 (18480 decoded bytes)
это воспроизвело порчу данных;9 малых ресурсов совпадали и скрывали проблему.
Первый вариант определял вызов по ra, но N64Recomp direct C calls не обновляют
его как MIPS JAL: ни одной поправки не произошло (v31, runner86).

Теперь hook перед подтверждённым JAL8003407C отмечает следующий вызов2730C.
Проверяются адрес buffer8007EF00 и размер; только полный3FF превращается в400.
Исходный2730C продолжает real queued PI DMA четырьмя порциями256, без memcpy stub.
V32:8 full refills,10/10 resources совпали. V36:8 refills,11/11 resources совпали,
включая дополнительный0B99 (ROM4DB330,8240 decoded bytes).

Снимок нового ресурса снимается перед модификацией вызывающим кодом. После
запуска runner сравнивает его с независимым Python-декодером. Это проверка
результата, не подмена игрового декодера; native_exit_code сохранён отдельно
от ошибки сравнения. Все бинарные снимки остаются вне Git.

Адаптацию нельзя распространять на все нечётные DMA: поведение малых первых
блоков отличается. Первичный код для сопоставления аппаратной модели:
[ares PI dmaWrite](https://github.com/ares-emulator/ares/blob/master/ares/n64/pi/dma.cpp).
Решающая локальная проверка — отрицательный v31 и положительный v32 на тех же
реальных данных; hashes сохранены в metadata.

## Память и ограничения эксперимента

Как и в v24, live target генерирует SHA-проверенную копию events.cpp с graphics
SP completion после разбора RT64, затем штатным DP completion. Это ограниченный
эксперимент, не доказанное общее исправление lifetime и не проверка исходного
темпа. Долговременная работа, смена сцен, nested lists, textures, матрицы и
CPU framebuffer feedback требуют отдельного исследования третьей игры.
Все32 зависимые деревья и Dora64 остались без изменений.

Ограничения:32 tasks либо15 секунд после setup; до2 секунд ожидания разбора
принятой задачи на fail-stop; аварийное завершение не проверяет штатный shutdown
и запись pipeline cache. DORA3_CAPTURE_GRAPHICS в live режиме отвергается;
старый безопасный private capture с VI доступен в default diagnostic target.
Реального ввода, аудиоустройства, Windows/Android live сборок пока нет.

Ближайший шаг: controller callbacks с настоящими кнопками/стиком frontend,
прохождение обычной ветви startup, затем SDL audio и проверка следующей сцены.
Улучшения камеры/широкого экрана/частоты остаются после устойчивого исходного цикла.

## Воспроизведение

Из корня проекта после bootstrap зависимостей/генератора. Значение ROM — свой
файл с проверенным хэшем. Для повторения выбирать свежие generation/run пути.
Нужны Linux, SDL2 development files и Vulkan; Windows/Android live ещё не собраны.

~~~bash
python3 tools/generate_startup.py --rom "$ROM" --output-dir build-local/startup-live-new
python3 tools/generate_audio_rsp.py --rom "$ROM" --output-dir build-local/audio-live-new
cmake -S research/runtime -B build-local/live-new -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DDORA3_LIVE_RT64=ON \
  -DDORA3_GENERATED_DIR="$PWD/build-local/startup-live-new" \
  -DDORA3_AUDIO_GENERATED_DIR="$PWD/build-local/audio-live-new"
cmake --build build-local/live-new --target dora3_startup -j6
python3 tools/run_startup.py --live --rom "$ROM" \
  --executable build-local/live-new/dora3_startup --run-dir build-local/run-live-new
~~~

Чтобы переиспользовать уже собранный RT64 replay target, можно вместо этого
конфигурировать research/graphics-replay с DORA3_BUILD_LIVE_STARTUP=ON и теми же
DORA3_*_GENERATED_DIR. Executable будет runtime-startup/dora3_startup внутри
этого build directory. Именно такой вариант проверен в build-local/graphics-replay.
Runner даёт setup до180 секунд; результат и журнал сохраняются локально.
Ожидаемый текущий результат:78 на лимите32 graphics tasks, pending пуст,
оба оверлея зарегистрированы после bytewise DMA verification,11 resources совпали.
Контроллер не подключён, поэтому исходная игра показывает соответствующий экран.
Private state/resources/*.bin содержит оригинальные данные; эти файлы запрещено
включать в Git или исходные архивы. Никакого ROM/resource download нет.

Отдельная сборка DORA3_LIVE_RT64=OFF с теми же generated CPU sources также прошла
границу78 (research/history/startup-v36-diagnostic.json). Количество audio callbacks
до ранней диагностической остановки зависит от планирования хоста.
