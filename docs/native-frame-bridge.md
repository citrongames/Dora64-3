# Приём настоящих кадров игровой очередью

2026-09-29. Продолжение native-frame-scheduler.md, база cf2eb7c.

## Что подключено

Генератор v62 вставляет вызов `dora3_native_game_message` перед800278F4,
сразу после osRecvMesg игровой очереди801A99E0. Проверяются слова ROM у вызова,
точки возврата, начала цикла и последующего `lh`. Только специальное значение
FFFFFF03 уходит в отдельный обработчик и возвращается к приёму сообщения.
Обычные сообщения выполняют исходный путь. Код не меняет частоту VI/AI.

Это уже hook в собираемой игре, а не только модель очереди. Однако **активации
Native Manual и подключённой сцены пока нет**. По умолчанию отправитель не работает,
новый поток/таймер не создаётся. Original и текущая реализация Manual остаются
прежними. test-024 остаётся последним переданным пользователю EXE.

FrameBridge соединяет предыдущие часы/банки с WakeMailbox. Вход требует
проверенного обработчика сцены и подтверждения безопасной границы исходных задач.
Токен сохраняется до доставки даже при переключении FPS/сцены. Старые/пустые
специальные сообщения поглощаются и никогда не разыменовываются как указатели.
Перед обработчиком кадра копируется recomp_context: новый вызов не должен
испортить s0/s1 или указатель стека оригинального message loop. Пауза801AA680=1
отключает новую доставку до выполнения callback.

## Причина изменения транспорта

Публичный enqueue_external_message возвращает void. Положенный в host-очередь
запрос ещё не доставлен в гостевую очередь. В do_send неблокирующая запись может
не пройти из-за её заполнения; при requeue=false runtime молча удаляет сообщение.
Для единственного native wake это означало бы навсегда занятый mailbox и остановку
новых кадров. Это выявлено по исходникам; пользовательский вылет этим не объяснялся.

В build-local копии pinned mesgqueue.cpp добавлен узкий sender: возвращает результат
host enqueue и всегда задаёт requeue=true. Пока гостевая очередь заполнена,
один запрос сохраняется. В каждом из трёх путей повторной постановки потеря именно
native wake при нехватке host-памяти приводит к bad_alloc, а не скрытому зависанию.
Начальный отказ/исключение sender отменяет mailbox и pending token без расхода времени.
Реальное исчерпание памяти не моделировалось: проверялся отказ/исключение отправителя.
Обычные политики requeue для VI/AI/SP/DP не изменены.

Пинованные зависимости не редактируются. Не добавлены собственные guest-RAM writes
из host-потока, динамический контейнер на каждый кадр или лимит времени игры.

## Сброс

Pinned recomp.cpp сначала ждёт остановки guest threads, затем reset_timers,
reset_events (SP sentinel и graphics/screen-update barrier), затем очищает внешние
очереди, и лишь после этого очищает RDRAM. В начало reset_message_queues вставлен
сброс FrameBridge. Для этого порядка дополнительно проверяется SHA-256 recomp.cpp;
events.cpp уже был закреплён по хэшу. CMake следит за обоими исходниками.

Сброс исключает producer, выключает часы, очищает mailbox и реестр старых банков.
Поколение/серийный номер не обнуляются: поздний completion не освободит новый банк.
Обычный leave по-прежнему сохраняет занятые банки. Нельзя вызывать reset_after_runtime_barrier
для произвольной смены сцены или FPS — он требует остановленных потребителей.
Будущий таймер должен завершаться до уничтожения runtime; сейчас такого таймера нет.

## Проверка

`python3 tools/check_native_frame_bridge.py --generated build-local/startup-v62`
и отдельный запуск с `--sanitizer thread` компилируют **настоящую adapted mesgqueue.cpp**
и **оригинальный8002787C с новым hook**, исполняют их на искусственной RAM.
Системный thread scheduler и scene callbacks заменены проверяемыми stubs.
Игра/окно/GPU не запускаются.

Проверены:

- сохранение native wake при заполненной очереди во всех трёх receive-путях;
- сохранение запрета доставки при выключенных N64 interrupts;
- раздельная обработка native / обычного VI / завершения задачи / паузы;
- только VI вызывает исходные lifetime/retirement/update/build;
- исходное task completion уменьшает исходный счётчик незавершённых задач;
- сохранение регистров loop, даже когда frame callback полностью их затирает;
- ранняя доставка до возврата sender, отказ и исключение sender;
- устаревшие сообщения после смены частоты, сцены, выхода в Original;
- сброс с опубликованным банком и ещё одним внешним запросом; повторный вход;
-2000 доставок с отдельным host-производителем и главным потребителем.

ASan/LSan не выявили ошибок в этом стенде. TSan не сообщил гонок, однако GCC
предупреждает, что atomic_thread_fence в pinned concurrentqueue не инструментируется.
Это ограничение проверки записано в JSON; не заявляется доказательство отсутствия
любых гонок сторонней очереди. Проверка сброса моделирует уже достигнутый барьер,
а реальный порядок подтверждён чтением и хэшами pinned runtime.

## Следующая незакрытая граница

Для включения сцены ещё нужны графический pump отдельно от scheduler retrace,
привязка GuestTask/HostRead к реальным подтверждениям и публикация нужного framebuffer
после CPU overlay. Проверенный parsed(dl) означает окончание разбора display list,
но updateScreen позже ещё читает framebuffer. Он берёт graphics_rdram_mutex и
создаёт owned present.storage; нельзя объявить весь present завершённым на parsed.
Original scheduler ждёт совпадения current/next framebuffer, защёлкиваемых на VI.
Удалить эту проверку без нового протокола показа недостаточно для частот выше60.

Затем можно включить проверенную2D-сцену через существующий Manual и отдельно
конвертировать обновления сцены, движение, физику, камеру, скрипты и анимации.
Ни renderer interpolation, ни ускорение всех VI не заменяют эти изменения.
