# Test-019 — безопасное отложенное освобождение парных вершин

Исправление относится к реестру800DD420 и буферам object+6C/+70, исследованным
в paired-vertex-lifetime.md. Оно не покрывает автоматически resource registry801AEC00,
прямые free других объектов, все вложенные DL/текстуры или raw RDP.

## Причины и исправление

Оригинальный16-tick таймер продолжал истекать при ещё не разобранных кадрах.
Оригинальная очередь100 записей также теряла дополнительные запросы, хотя
владелец уже обнулял указатели. Guard работает через существующие entry trace
оригинальных функций. CPU generation startup-v61 и оригинальные тела не изменены.

Два host task slots соответствуют двум кадровым банкам. На входе8002FF64 выдаётся
монотонный ticket уже строящемуся кадру; это важно для удаления объекта до SendMesg.
Вход8002FE20 помечает начало публикации (до собственно очереди8002FF50).
После возврата RT64 processDisplayLists, включая FullSync, live frontend отмечает
ticket завершённым. Здесь ещё не утверждается завершение всего GPU/present.
Банк запрещено повторно начинать до окончания разбора его предыдущей задачи.

На входе80038B10 сохраняются pointer и последний выданный ticket. Перед исходным
tick80038B4C запись с countdown=1 удерживается на1, пока активна хотя бы одна задача
с ticket<=сохранённого. Технически hook пишет2, исходный tick уменьшает обратно до1.
После завершения этих задач исходный free проходит при следующем tick. Более новые
кадры не продлевают ожидание; нет ожидания глобального outstanding==0 и блокировки
игрового потока до завершения графики. Исходные16 ticks сохраняются как минимум.

Если100 guest slots заняты, исходный enqueue возвращается как раньше, а pointer
сохраняется в host overflow vector с16 ticks и ticket. По готовности выполняется
оригинальный80033C50/80033BA4. Этот проверенный wrapper+allocator не вызывает SDK,
не меняет планирование и не выполняет DMA. Hook сохраняет/восстанавливает весь
recomp_context вокруг этого вызова; scratch stack ниже текущего SP используется
как при обычном вызове. Освобождение не выполняется на потоке renderer.

Число дополнительных записей имеет консервативную верхнюю границу4MiB/16 — физическая
RDRAM, делённая на выравнивание аллокатора. Это не лимит времени/числа кадров.
Пустой vector может сохранять capacity до смены heap; записи не накапливаются
после освобождения. При heap reset его backing storage освобождается.
Строка RESOURCE RETIRE overflow retained показывает сохранение дополнительного
запроса; логирование — только на степенях двойки счётчика.

## Переходы и сброс

У оригинала это разные операции:

- 80038AE4 очищает только реестр; вызывается через8003B7D0 из инициализации подсистем.
 Guard переносит ещё живые записи в host overflow с оставшимся countdown/ticket.
 Иначе такой reset снова потерял бы указатели. Самостоятельный registry reset
 не является разрешением немедленно освобождать ещё читаемые данные.
- 80033A14 переинициализирует heap. Перед успешной ветвью (size>=32) guard убирает
 старые guest/host retirement records. Старые указатели нельзя позднее передавать
 новому heap: адреса могут принадлежать уже другим объектам. Сами старые allocations
 поглощаются переинициализацией всей области, индивидуальный free не нужен.
- Guest-переход800271B0 ждёт outstanding=0 перед cleanup/возобновлением process.
 Guard дополнительно проверяет, что при heap init нет опубликованных неразобранных
 задач. Строящийся новый кадр может выполнять scene init до публикации; его ticket
 сохраняется. Нарушение протокола диагностируется, не маскируется ранним free.
- Полный runtime reset очищает ledger на существующем graphics/guest barrier.

Мьютекс защищает только два task slots и счётчик tickets. Guest retirement records
обрабатываются одним запланированным CPU-потоком; renderer их не читает. Ни mutex
ledger, ни graphics_rdram_mutex не удерживаются через гостевые SDK-вызовы.

## Проверки и границы

tools/check_retirement_guard.py исполняет настоящие generated registry init,
heap init, enqueue и tick вместе с production guard. Free endpoint регистрирует
адреса; реальный allocator проверялся отдельно в test-017. Проверены:

- прежняя задержка16 ticks при отсутствии графики;
- retired resource во время построения, публикации и задержанного разбора;
- завершение задач в обратном порядке и продолжение новых кадров;
- все102 освобождения при переполнении исходной очереди100;
-100 повторных переполнений без оставшихся запросов;
- registry-only reset с сохранением остатка таймера;
- конкурентный consumer и reuse адреса после heap reset.

ASan/LSan и отдельно ThreadSanitizer: exit0. Это стенды без игры и GPU, не доказательство
полной совместимости всех сцен. Windows RT64 и Linux diagnostic скомпилированы.
Dora64/32 зависимости не изменены. В diagnostic frontend guard выключен, поскольку
там нет асинхронного RT64 consumer; тест включает его явно.

```sh
python3 tools/check_retirement_guard.py --generated build-local/startup-v61 --sanitizer address
python3 tools/check_retirement_guard.py --generated build-local/startup-v61 --sanitizer thread
```

Отчёты research/retirement-guard-address-check.json,
research/retirement-guard-thread-check.json, research/windows-build-check.json.
Пользовательская сборка test-019; saves/settings прежние, ROM только рядом с EXE,
без лимита длительности. Остаток аудита: отдельный512-slot resource registry,
прочие direct free/CPU framebuffer writers, raw RDP и реальный расход GPU-памяти.
