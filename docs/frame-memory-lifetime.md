# Срок жизни памяти кадра Doraemon 3

Продолжение: [test-017, CPU framebuffer и память](synchronization-memory.md).
В нём закрыта описанная ниже переходная CPU-копия и ограничена periodic очередь;
оставшиеся вопросы других производителей ресурсов сохраняются.

Дата: 2026-09-29. База аудита: `1354513`, Windows test-016; изменение света
разрабатывается отдельно в ветке `frame-memory-lifetime`. test-016 и его общие
DLL/настройки/сохранения не заменяются. Это статический аудит и компонентная
проверка, не результат полного прохождения или испытаний GPU/Android.

## Установленный протокол третьей игры

Адреса относятся только к N3DJ rev0 из `recomp/rom.lock.json`. Основание —
оригинальные инструкции ROM; SHA-256 рассмотренных тел сохраняет
`research/frame-memory-check.json`. Дизассемблирование остаётся в build-local.

| Объект | Адрес / размер | Использование |
|---|---|---|
| Банк 0 | `8010E310`, размер `31728` | Заголовки задачи и данные кадра |
| Банк 1 | `8013FA38`, размер `31728` | Второй банк; конец `80171160` |
| OSTask | банк + `10` | Встроен в OSScTask |
| Область кадровых данных | банк + `108` .. + `12328` | Размер `12220`; не следует называть весь диапазон пулом матриц |
| Основной DL | банк + `12328` .. конец банка | Начала `80120638` / `80151D60`, вместимость `1F400` байт |
| Текущий банк | `80171CC0` | Устанавливает `8002FF64` |
| База данных / курсор DL | `801B1608` / `801B1424` | Меняются при сборке кадра |
| Число незавершённых кадров | `801AA618` | Обычный путь строит кадр при значении < 2 |
| Очередь завершения игры | `801A99E0` | Сообщение типа 2 уменьшает счётчик |
| Общий свет | `8006FB70` .. `8006FB98` | Ambient и два направленных источника; вне обоих банков |
| Начальные color FB | `803B5000`, `803DA800` | 320×240×16 бит; текущие указатели нужно читать из игры |

`8002787C` принимает retrace/completion. На retrace часть обновлений выполняется
ещё до проверки числа незавершённых кадров; поэтому этот счётчик нельзя считать
блокировкой всей игровой RAM. Обычный путь чередует два банка.

`8002FF64` задаёт банк и курсоры, вызывает игровые render-процессы, дописывает
FullSync/EndDL и вызывает `8002FE20`. Последняя заполняет task.data_ptr/size,
ставит OSScTask flags=`63` и передаёт задачу через osSendMesg в `8002FF50`.
В delay slot `8002FF54` ещё записывается framebuffer в OSScTask + `0C`.

`80026E24` запускает работу SP/DP. В `80026D40` сообщение завершения отправляется
только после обнуления обоих pending-битов task + `04`. На стороне порта
`prepare_runtime_timing.py` переносит SP completion за `send_dl`; DP completion
тоже следует после него. Так обычное повторное использование банка не должно
опережать разбор его DL. Это гарантия рассмотренного пути, а не доказательство
отсутствия любых посторонних записей в банки.

Матрицы камеры и look-at из `8002F2C8` лежат относительно текущей базы:
`+100` (float), `+FB80` (fixed), `+FBE0/+FBF0` (look-at). Они входят в банк.
`8002F4E0` выдаёт матрицу по индексу относительно этой же базы. Это не доказывает,
что все матрицы, вершины и вложенные DL каждого оверлея лежат там же.

## Подтверждённый дефект владения общим светом и исправление

DL содержит MoveMem-ссылки на `8006FB78`, `8006FB88`, `8006FB70`.
`80027B84` пишет три компоненты направления в первый или второй источник;
его вызывают resident-функции `80027CD0`, `80027D24` и render-пути scene1,
например `801BB334` и `801F9C88`. Это изменяемая память, а не ROM-константы.
RT64 `RSP::setLight` читает указатель позднее на графическом потоке.

При построении второго кадра его свет может заменить данные, на которые
ссылается ещё не разобранный первый кадр. Задержка SP completion не устраняет
это: два банка могут находиться в работе одновременно, а источник света один.
Компонентный стенд воспроизводит именно такой допустимый порядок; появление
видимого дефекта в пользовательском прохождении пока не зафиксировано.

Добавлен снимок **40 байт на задачу** перед `osSendMesg` в `8002FF50`:

1. Hook сохраняет свет по идентичности банка до публикации OSScTask.
2. Два host-слота защищены mutex. Нельзя повторно опубликовать занятый слот.
3. Перед HLE-разбором RT64 забирает соответствующий снимок в собственную копию.
4. Существующий `lightDataCallback` возвращает эту копию только для трёх
   проверенных адресов. Остальные адреса идут через прежний путь RT64.
5. После разбора callback больше не подменяет свет; raw RDP не использует снимок.
   При reset-barrier pending-снимки очищаются.

Word-swapped порядок байтов сохраняется. RT64 читает 16 байт даже для ambient:
все три чтения целиком укладываются в диапазон 40 байт. Размер `RSP::Light`
проверяется при компиляции. Захват выключен у diagnostic frontend без RT64.
Место hook проверяется по словам ROM при генерации; стенд дополнительно
проверяет настоящий generated-код и выполнение delay slot до публикации.

Не добавлены новые guest-пулы, полная копия RDRAM или адреса первой игры.
Пинованные библиотеки не редактировались: использован уже имеющийся API RT64.
Режим FPS, число кадров в работе и исходная скорость игры не менялись.

## Что уже обеспечивает renderer/runtime

| Путь чтения | Результат проверки |
|---|---|
| HLE DL / матрицы / вершины | Разбираются синхронно внутри `send_dl`; RT64 копирует разобранные данные в свои структуры |
| Обычный PI/EPi DMA | `pi.cpp` держит тот же `graphics_rdram_mutex`, что HLE/raw-разбор; блокировка действует и на desktop, не только Android |
| Геометрические snapshots RT64 | `State::fromRDRAM` поддерживает диапазоны, но сами по себе они не охватывают все источники текстур/FB |
| Текстуры, TLUT | В `RDP::loadTile/loadBlock/loadTLUT` есть чтение непосредственно из `state->RDRAM`; геометрический snapshot их не защищает |
| Render-to-RAM | В рассмотренной ветке FullSync RT64 ждёт GPU, затем `copyNativeToRAM`; сообщение DP нельзя отождествлять с завершением всего последующего показа кадра |
| Present | `updateScreen` проверяет/копирует live framebuffer, затем передаёт owned `present.storage`; важен срок жизни исходника во время самой копии |

## Оставшиеся вопросы, не скрытые исправлением света

- **CPU framebuffer / VI.** `800271B0` выполняет CPU-копию между FB только
  при отсутствии незавершённых игровых кадров. Но ScreenUpdateAction имеет
  отдельную очередь и в рассмотренном runtime не берёт graphics_rdram_mutex.
  Проверка счётчика задач сама по себе не является взаимным исключением с VI.
  Не установлено, что данный путь реально пишет тот же FB одновременно с VI.
  Добавление mutex только в `updateScreen` не защитит обычные guest-store.
  Нужен разбор всех производителей CPU-изображения и согласованная граница записи.
- **Общие ресурсы и вложенные DL.** `80030D00`/`80038B4C` обновляют и освобождают
  отложенные ресурсы до проверки числа кадров. Карта всех динамических ссылок
  на ресурсы из всех 49 известных регионов ещё не доказана; простое отсутствие
  вылета не заменяет её. Для нового снимка сначала нужен конкретный производитель,
  потребитель и момент повторного использования.
- **Прямой RDP.** Команды и текстуры читаются из live RAM; отдельная фиксация
  источников не добавлена. Установленная очередь/DP busy — отдельный протокол,
  который ещё требует игровых наблюдений.
- **GPU/Android.** Исправления coherency/barriers/descriptors/render-target init
  первой игры сохранены в зависимостях. Эта работа не является их проверкой на
  третьей игре или на устройствах.

Итог аудита: карта обычного кадра установлена, один конкретный общий источник
защищён и проверен без GPU. Универсальная безопасность всей игровой/графической
памяти не заявляется. Остаточные вопросы перечислены отдельно от исправленного.

## Воспроизведение

```sh
python3 tools/generate_startup.py --rom "$ROM" --output-dir build-local/startup-v60
python3 tools/check_frame_memory.py --rom "$ROM" --generated build-local/startup-v60
```

Первую команду выполнять только для нового output-dir; ROM должен совпасть с lock.
Стенд компилирует два оригинальных тела (публикация задачи и запись света),
запускает только компонент без игры и рендера. Он проверяет два отложенных кадра,
снимок уже внутри точки отправки, чтения RT64 по 16 байт, повторное использование
и reset. Сравнение с изменённым live-источником подтверждает сам механизм ошибки.
Generated-тела и любые игровые байты остаются в ignored build-local.

Для Windows helper по умолчанию выбирает v60. Результаты компиляции фиксируются
отдельно от отчёта test-016, чтобы не подменять базу текущего прохождения.
