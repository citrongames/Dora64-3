# Аппаратная граница Dora64-3 — test-016

Шесть прежних pending-точек реализованы. Из них пять — функции libultra,
шестая — оригинальный декодер шрифта с чтением ROM через адрес картриджа.
В известном графе вызовов больше нет pending: 4778 оригинальных функций,
44 прежние замены SDK и 5 новых нативных обработчиков. Это не доказательство
полноты всех косвенных переходов ROM или отсутствия игровых ошибок.

## Проверенная идентификация

| VRAM | Назначение | Реализация |
| --- | --- | --- |
| 80045520 | Декодер шрифта для экрана Controller Pak | Оригинальные 0x210 байт рекомпилированы; только LW в 8004552C/80045574/800455DC проходят через чтение шины ROM/RAM |
| 800586F0 | osDpSetNextBuffer | a0 — адрес; 64-битный размер a2:a3; очередь прямых команд RDP в RT64; отказ при занятой передаче |
| 80058A50 | __osSiRawStartDma | 64-байтные WRITE/READ PIF, разбор каналов Joybus, реальные ввод/EEPROM, SI-событие после каждой передачи |
| 8005F1C0 | __osDisableInt | Возвращает прежний IE; запрещает доставку внешних сообщений и вытеснение текущего гостевого потока |
| 8005F230 | __osRestoreInt | Восстанавливает через OR сохранённого IE; на переходе 0→1 доставляет отложенные сообщения и проверяет готовые потоки |
| 800604E0 | __osSpSetPc | Записывает выровненный PC только в остановленном состоянии; занятость связана с реальной отправкой/завершением RSP-задач |

Пять нативных замен имеют SHA-256 оригинальных тел в `recomp/startup.json`.
Несовпадение ROM останавливает генерацию. Три инструкции чтения декодера
проверяются перед вставкой хуков. Извлечённый код/шрифт остаётся в build-local.

## Семантика и интеграция

RDP: новая работа проходит через ту же последовательную графическую очередь,
что и существующие RSP display lists. RT64 получает `processDisplayLists(...,
false)` с началом и концом сырых команд, без сброса накопленного состояния DP.
Сам RT64 вызывает DP interrupt при FullSync. После разбора буфера снимается
занятость передачи и доставляются зарегистрированные FullSync-события.
Без FullSync событие DP не выдумывается; событие SP для сырых команд не создаётся.
RT64 сохраняет незавершённые многословные команды между буферами.

SI: WRITE сохраняет запрос и разбирает каналы при control bit 0; READ выполняет
обмен и копирует ответ в word-swapped RDRAM. Повторный READ снова опрашивает
контроллер без обязательной повторной WRITE, как требуется оптимизации libultra.
Различаются padding FF, end FE, пропуск/сброс канала, длины, overflow и no response.
Проверяются границы 64-байтного пакета и 4 MiB RAM. Передача синхронная на стороне
host, её завершение доставляется через обычную внешнюю очередь SI runtime.
При отключённых гостевых прерываниях сообщение остаётся отложенным.

Контроллер использует те же frontend callbacks и преобразование стика, что
высокоуровневый SDK. Подключён только обычный контроллер порта 0; Controller Pak,
Rumble Pak и RTC в текущем frontend не подключены. Отсутствующее устройство
возвращает отсутствие ответа, а не фиктивный успех. Добавление аксессуаров —
отдельная функциональность, а не оставшаяся pending-точка DMA.

EEPROM соответствует этой игре: 16 Kbit / 2048 байт / 256 блоков по 8 байт.
Команды identify/read/write используют существующие `save_read/save_write_ptr`,
то есть тот же защищённый буфер и поток записи, что SDK и общие saves. Второго
файла сохранений, теневой копии EEPROM и отдельного формата не создаётся.

IE хранится на гостевой поток, которому соответствует отдельный host thread.
Вложенные disable/restore сохраняют прежнее состояние. Адаптированы обычный,
блокирующий и timed пути доставки внешних сообщений, а также check_running_queue.
Это модель прерываний кооперативного runtime; тактовые задержки N64 не эмулируются.
RSP исполняется существующими нативными микрокодами/HLE, не универсальным
интерпретатором произвольного кода IMEM. PC и HALT отражают жизненный цикл этих задач.

## Первичные источники

- [Архив руководства Nintendo/SGI: DP API](https://ultra64.ca/files/documentation/online-manuals/man-v5-1/n64man/os/osDpSetNextBuffer.htm): сигнатура и буфер прямых команд.
- [SGI RSP Programmer’s Guide](https://ultra64.ca/files/documentation/silicon-graphics/SGI_Nintendo_64_RSP_Programmers_Guide.pdf), раздел интерфейсных функций, __osSpSetPc: PC меняется при HALT, иначе -1.
- [libdragon: реальный обмен SI/Joybus](https://github.com/DragonMinded/libdragon/blob/trunk/src/joybus/joybus.c): отдельные завершения WRITE и READ.
- [ares: PIF HLE](https://github.com/ares-emulator/ares/blob/master/ares/n64/pif/hle.cpp): разбор каналов на WRITE, исполнение на READ, управляющие байты и флаги ошибок.
- Оригинальные инструкции данного ROM: ABI, условия ветвления, CP0 IE и размеры.
- Закреплённые RT64 `rt64_interpreter.cpp`, `rt64_gbi_rdp.cpp`: обработка прямых команд, сохранение частей команд и FullSync → dpInterrupt.
- Закреплённые N64ModernRuntime `pi.cpp`, `input.cpp`, `threads.cpp`, `mesgqueue.cpp`, `scheduling.cpp`: общий save backend, ввод и кооперативные потоки.

Веб-источники просмотрены 2026-09-28; решение сверено с конкретным ROM и pins
этого проекта. Код стороннего эмулятора не копируется в проект.

## Воспроизводимая проверка

После обычного bootstrap и генерации CPU startup-v59:

```sh
python3 tools/check_hardware.py --rom "$ROM" --generated build-local/startup-v59
python3 tools/check_overlay_inventory.py --rom "$ROM" --generated build-local/startup-v59
```

Компонентный стенд не запускает игру, окно или графическое устройство. Он
использует настоящие исходники EEPROM, очереди сообщений и преобразования ввода
из закреплённого runtime; создание/переключение потоков и графический потребитель
заменены контролируемыми тестовыми точками. Проверено:

- вложенное IE, независимое IE другого потока, отложенное сообщение через все
  три пути чтения внешней очереди и доставка после restore;
- оба SI completion, busy/reentrant и ошибки адреса/направления/длины;
- повторный опрос контроллера, кнопки, стик, отсутствие второго контроллера;
- идентификация EEPROM, чтение всех 256 блоков, запись последнего блока без
  изменения остальных и чтение через общий SDK backend;
- o32 ABI 64-битного размера DP, busy/completion, нулевая длина и границы RAM;
- запись PC при HALT, отказ при занятом RSP, две задачи и два завершения;
- все 4320 байт результата оригинального декодера совпадают с независимым
  последовательным разбором битового потока; защитные зоны и стек сохранены.

Receipt — `research/hardware-check.json`, шрифтовые данные не коммитятся.
RDP подключён к настоящему RT64 и проверен компиляцией/чтением кода; реальное
исполнение этой ветки и картинка не проверялись без разрешённого пользовательского
запуска. Нулевой pending не означает подтверждённое полное прохождение.

## Изоляция зависимостей

`prepare_runtime_timing.py` создаёт только build-local копии трёх файлов runtime:
events, scheduling, mesgqueue. SHA-256 исходников закреплены; неизвестная версия
отклоняется. CMake заменяет только соответствующие translation units. Все
исходные dependency checkouts и работающий Dora64 сохраняются без изменений.
