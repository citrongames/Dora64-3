# Синхронизация и память: test-017

2026-09-29, продолжение аудита `frame-memory-lifetime.md`. Включает исправление
света из fc09480. CPU generation v61, audio-rsp-v1. Игра/renderer агентом не
запускались. Windows-сборка предназначена для прохождения пользователем.

## CPU framebuffer и RT64

Оригинальная `800271B0` копирует кадровые color buffers при смене сцены.
Ожидание нулевого счётчика задач исключает текущие игровые SP/DP-задачи, но
периодический `ScreenUpdateAction` может уже находиться в host-очереди.
В предыдущей реализации `State::updateScreen` читал/хэшировал live framebuffer
без согласования с этой CPU-копией. Конкретный визуальный сбой у пользователя
не зафиксирован; отсутствие общей границы доступа установлено по коду.

Добавлена общая блокировка `graphics_rdram_mutex`:

- В guest-функции — непосредственно перед `800272BC`, после всех вызовов
  очистки списков/возобновления процессов; освобождение перед `800272F8`.
  Внутри только исходный цикл чтения/записи и ветка нулевого размера.
  Хуки не охватывают SDK, переключение гостевых потоков, PI или чужие функции.
- В `LiveContext::update_screen` — на время чтений RT64. Тот же mutex уже
  защищает PI DMA и разбор HLE/raw RDP. Lock-order между framebuffer copy и
  RT64 не вводит гостевого ожидания очереди, удерживающего этот mutex.
- Ранние выходы функции доходят до общего epilogue: thread-local признак
  не допускает unlock без предшествующего lock. Нулевая область также проходит
  парные hooks. Они не меняют данные или регистры.

Стенд сравнил всю синтетическую RDRAM и весь recomp_context с тем же оригинальным
телом без двух hooks: оба банка, обычная копия, нулевой размер, pending-задача
и очистка списков. Отдельный конкурентный сценарий удерживает mutex на чтении
и подтверждает, что оригинальные CPU-store не начинаются до его освобождения.
Зависимости внешних игровых вызовов в этом компоненте заменены тестовыми
конечными точками: это не проверка всей смены сцены.

## Накопление запросов показа

В pinned runtime VI-поток безусловно ставил `ScreenUpdateAction` каждый retrace
в динамическую `BlockingConcurrentQueue<Action>`. При отставании графического
потока очередь могла расти вместе с продолжительностью задержки. Это удержание
всё новых задач, а не потеря указателя, но расход памяти и задержка росли бы.

Адаптация build-local допускает один незавершённый **периодический** запрос показа,
включая время его обработки. Повторные запросы пока он занят объединяются;
после завершения следующий retrace получает новую возможность публикации.
Старый запрос не переносится через графические задачи и не заменяет свои VI-регистры
на регистры будущего кадра. Подготовительный DummyWorkload ограничен тем же разрешением.

VI/AI сообщения игре, SP/DP, графические задачи, reset-barrier и явный механизм
CPU screen publication из runtime не проходят через этот gate. В Dora3 последний
не подключён. Нет ограничения продолжительности сеанса, числа игровых кадров
или скорости игры. Это ограничение накопления дублирующей работы показа.
На медленном renderer промежуточные запросы показа могут объединяться; влияние
на плавность реального вывода проверяется пользователем.

В стенде 2 миллиона periodic ticks обработаны за 2000 циклов искусственно
занятого потребителя. В очереди остаётся один запрос, включая период обработки;
после complete новый запрос снова принимается. Проверены настоящая moodycamel
queue и тот же gate, который использует адаптированный events.cpp. Полный
runtime/RT64 scheduler в стенде не исполнялся; интеграция прошла компиляцию.

## Владение памятью и границы проверки утечек

| Область | Что установлено |
|---|---|
| Первичный ROM-буфер | В main 16-МиБ vector использовался для хэша и заголовка, затем удерживался всё время `recomp::start`. После регистрации игры освобождается; runtime сам читает ROM по сохранённому пути и владеет рабочим буфером (`read_file`, `set_rom_contents`) |
| Свет | Два фиксированных host-слота и одна копия consumer по40 байт; контейнер не растёт с кадрами |
| Trace/overlay учёт | Фиксированный массив известных overlay-регионов; thread-local set только известных адресов и ROM-идентичностей. Это удержание диагностических записей, не per-frame append |
| PCM | Временный vector освобождается после SDL_QueueAudio; устройство закрывается при смене частоты и shutdown. Текущая проверка stalled audio queue прежняя, не изменена |
| Игровой heap | `80033A14` init, `80033A88` best-fit, `80033BA4` free/coalesce. 2000 циклов ×64 allocations/free вернули всю область128КиБ к одному свободному блоку; аллокатор не изменён |
| Runtime threads | Cleaner делает host_thread.join + delete контекста; штатный stop ждёт game/events/cleaner/saving, затем освобождает RDRAM |
| RT64 queues | Workload и Present — массивы по4 элемента. Их внутренние vectors могут сохранять capacity по максимуму; это не доказанная утечка |
| Текстуры RT64 | Есть возрастное eviction, удаление hashMap entry и отложенное delete после lockCounter=0. Replacement pool имеет отдельную политику. Выполнение этих условий на полном прохождении ещё не измерено |
| Завершение RT64 | `Application::end` освобождает state, queues, uploaders, shader/texture cache, workers, swapchain/device. Успешное фактическое завершение GPU на каждом драйвере не подтверждено этим аудитом |

Стенд запущен с **AddressSanitizer + LeakSanitizer**, `detect_leaks=1`, остановка
на ошибке и ненулевой exit при утечке. Итог exit0, без сообщений о нарушениях.
Это результат компонента с синтетической памятью и настоящими выделениями/
освобождениями, а не гарантия отсутствия всех утечек игрового процесса или драйвера.

В runtime.log добавлена строка `MEMORY` примерно раз в минуту: Windows working
set и private bytes, число принятых/объединённых periodic requests. На Linux
читается resident из /proc/self/statm; private_bytes=0 означает, что этот показатель
там не собирается. `available=0` означает неудачный замер, а не нулевой расход.
Один высокий замер или рост кэша после первой новой сцены не доказывает утечку;
полезно сравнить повторные посещения уже загруженных сцен в одном запуске.
GPU-local memory этим показателем не измеряется.

## Остаётся исследовать

Динамические ресурсы: освобождение в `80030D00` и `80038B4C` основано на игровых
таймерах, не на host GPU fence. Наличие ожидания SP/DP для банков не доказывает
срок жизни всех вложенных DL, текстур и вершин. Не вводить задержку «до нуля всех
кадров» в free без анализа: при постоянной очереди она сама может удерживать память.
Все CPU-производители текстовых/прочих FB-данных и прямой RDP пока не охвачены
новыми игровыми hooks. Временное зависание драйвера и реальная VRAM требуют
отдельных наблюдений. Старые адреса/пулы первой игры не переносились.

research/frame-memory-check.json и research/windows-build-check.json.

вызывается и при unlock. Сигнал сделан одноразовым; production-код из-за этого
не менялся. Windows live/RT64 и Linux diagnostic скомпилированы без запуска.
